# Working Together

This document answers a simple question:

If someone likes the project, how can they work with us without turning the open-source core into a bait-and-switch?

For the public summary of support and sponsorship paths, start with [`../FUNDING.md`](../FUNDING.md). This file focuses on principles and conversation style.

## Open-source first

The repository remains the public core:

- technical users can run it themselves,
- docs stay public,
- improvements to the engine should continue to benefit everyone.

## Simple collaboration paths

### 1. Friendly technical conversation

Best when:

- someone is curious,
- they are not sure whether the project fits,
- they want help understanding deployment or evaluation.

Outcome:

- no pressure,
- identify whether a pilot even makes sense,
- point them to the smallest honest next step.

### 2. Paid pilot setup

Best when:

- the problem is real,
- the team wants help getting to value faster,
- they need a narrow, controlled rollout.

Typical scope:

- install or deployment help,
- criteria tuning,
- pilot setup,
- review of first results.

### 3. On-prem implementation help

Best when:

- the customer already knows they want the workflow,
- privacy and infrastructure control matter,
- the deployment needs to be stable and repeatable.

Typical scope:

- deployment,
- infrastructure review,
- local-first architecture choices,
- business-specific adaptations.

### 4. Ongoing support

Best when:

- the product is already in use,
- the team wants predictable help over time,
- there are regular operational or tuning questions.

Typical scope:

- upgrades,
- deployment adjustments,
- prompt and criteria tuning,
- analytics or reporting improvements.

### 5. Sponsorship or contribution

Best when:

- someone values the mission,
- they want the project to keep improving in the open,
- they are not buying a formal service package.

## How to talk about money

Use this principle:

- do not sell pressure,
- do not sell fear,
- do not sell artificial scarcity.

Instead:

- explain the open-source path,
- explain the paid help path,
- let the other person choose whether speed, clarity, or support is worth paying for.

## Good answer to “How can we work with you?”

Use something like this:

> The repo is open and you can evaluate it yourself. If you want, we can also help in a more hands-on way: first as a narrow pilot, then as deployment or on-prem support if the workflow proves useful. The goal is to find the smallest honest step that helps your team.

## Rule of thumb

If a collaboration option would force you to weaken the open-source core in order to make money, it is probably the wrong option right now.
