# Funding and Support

This repository is open source under the MIT license.

If the project helps your team or you want to accelerate its roadmap, there are several ways to support development without changing that core promise.

## Why this project matters

The project is built around a simple idea:

- help teams review more calls without giving up privacy,
- make QA feedback clearer and more actionable,
- keep useful speech analytics available in a self-hosted, open-source form.

Support helps keep that value public instead of turning the project into a closed black box.

If you want the cleanest summary of collaboration paths, see [`docs/WORKING_TOGETHER.md`](docs/WORKING_TOGETHER.md).

## Ways to support the project

### 1. Paid pilot

Best for teams that want to validate the product on a real workflow with limited scope.

Typical pilot help:

- environment review,
- deployment assistance,
- criteria and template tuning,
- interpretation of early results,
- calm evaluation of whether the product is actually useful for your team.

### 2. On-prem implementation

Best for organizations that need a working self-hosted setup, privacy-sensitive handling, and business-specific configuration.

Typical implementation help:

- installation and configuration,
- integration planning,
- report tuning,
- rollout support.

### 3. Ongoing support

Best for teams that already use the system and want predictable maintenance.

Typical support topics:

- upgrades,
- troubleshooting,
- prompt and criteria tuning,
- analytics adjustments,
- operational guidance.

### 4. Sponsorship or donation

Best for people who want to help the project grow even if they do not need a full implementation.

Sponsorship helps fund:

- documentation,
- easier onboarding,
- better tests and CI,
- API and UI improvements,
- new integrations driven by real demand.

It also helps keep the project useful for teams that care about privacy, budget control, and on-prem deployment.

## Collaboration philosophy

The goal is not to force every conversation into a sale.

The preferred path is:

- help people understand whether the project fits their problem,
- keep the open-source core genuinely useful,
- offer hands-on help only when it saves real time or de-risks deployment,
- let support, partnership, and revenue emerge from visible usefulness.

That keeps the project aligned with the reason it exists in the first place: freeing people from repetitive, low-value review work.

## What funding should accelerate

The highest-value roadmap items are:

- easier evaluation and onboarding,
- stronger pilot workflows on top of the shipped web/API surface,
- better saved-result review, export, and sharing flows,
- stronger quality gates and tests,
- real customer-driven integrations,
- local-first deployment profiles such as optional HTTP ASR for remote GPU hosts.

## Commercial model

The preferred model is:

- keep the open-source engine open,
- charge for deployment, speed, customization, and support when that is genuinely helpful,
- use sponsorship to fund public improvements that benefit everyone.

## What sponsorship unlocks for the commons

Sponsorship is not only about faster private delivery. It also funds public improvements such as:

- clearer onboarding,
- safer pilot deployment patterns,
- better docs and examples,
- stronger tests and CI,
- reusable integrations that stay in the open-source project.
